## 前言

SQL 注入从 1998 年被公开讨论至今已超过二十五年，却依然稳居 OWASP Top 10（2021 版 A03 注入类）和 CNVD 漏洞榜单前列。它并不"低级"——大量数据泄露事件的背后都是一条注入语句。本文面向开发与防守方，重审原理与防御。

<!--more-->

## 漏洞成因：数据被当成了代码

```java
// 反例：字符串拼接构造 SQL
String sql = "SELECT * FROM users WHERE name = '" + username + "'";
```

当 `username` 为 `' OR '1'='1` 时，拼接出的语句语义被彻底改变。SQL 注入的本质是**代码与数据没有边界**：用户输入跨越了"数据"的边界，成为了"语法"的一部分。

## 主要类型

| 类型 | 特征 | 典型场景 |
|---|---|---|
| 联合查询注入 | 通过 UNION 回显数据 | 老旧的直接回显页面 |
| 报错注入 | 利用数据库报错信息带出数据 | 开启详细错误回显的应用 |
| 布尔盲注 | 页面仅返回真/假两种状态 | 无回显登录接口 |
| 时间盲注 | 通过响应延迟推断数据 | 完全无差异响应的接口 |
| 二次注入 | 存储的数据在后续查询中被拼接 | 用户名→日志系统→后台查询 |
| 堆叠注入 | 一次执行多条语句 | SQL Server / PostgreSQL 特定配置 |

## 防御的正确姿势

### 1. 参数化查询（预编译）—— 根因防御

```java
// 正例：占位符传参，数据永远只是数据
PreparedStatement ps = conn.prepareStatement(
    "SELECT * FROM users WHERE name = ?");
ps.setString(1, username);
```

**注意**：预编译不是字符串拼接后再 `prepareStatement`，那没有任何防护效果。

### 2. ORM 不等于免疫

MyBatis 的 `${}` 是字符串拼接（危险），`#{}` 才是参数绑定（安全）。以下场景即使使用 ORM 依然常见注入：

- `ORDER BY ${sortField}` —— 排序字段无法参数化，必须用**白名单枚举**
- `LIKE '%${kw}%'` —— 应写成 `LIKE CONCAT('%', #{kw}, '%')`
- 动态表名 —— 只能白名单映射

### 3. 纵深防御

- **最小权限**：应用数据库账户仅授予必需的 SELECT/INSERT/UPDATE，禁用 DROP、FILE、xp_cmdshell 等高危权限
- **输入校验**：对整形参数强制类型转换，对枚举参数白名单校验
- **错误收敛**：生产环境关闭数据库错误详情回显，统一错误页
- **WAF 兜底**：拦截常见注入特征，但不可作为唯一防线（绕过手法极多）

### 4. 代码审计要点

- 全仓搜索拼接特征：`"SELECT" +`、`Statement.execute(`、`${`（MyBatis）
- 关注"二次注入"：入库时转义 ≠ 出库后安全
- 存储过程内部拼接动态 SQL 同样存在注入

## 检测与排查

- 历史日志中检索 `'`、`union select`、`sleep(`、`benchmark(` 等特征的请求
- 数据库审计：是否存在异常的 `information_schema` 查询、批量导出行为
- 上线前使用 sqlmap 等工具在**测试环境**自测（严禁对未授权系统使用）

## 小结

SQL 注入的根治方案二十年前就有——**参数化查询**。它至今泛滥的原因不是技术难题，而是开发习惯与存量代码。把"禁止拼接 SQL"写进编码规范、接进 CI 扫描，比任何 WAF 都可靠。

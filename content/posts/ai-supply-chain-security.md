## 前言

企业落地 AI 应用时，注意力往往集中在"模型好不好用"，却忽略了 AI 工程栈引入了**三条全新的供应链风险通道**：模型权重文件、Python/ML 依赖生态、训练与微调数据。任何一条被污染，后果都可能比传统软件供应链事件更严重——因为模型文件本质上就是"可执行的代码载体"。

<!--more-->

## 风险面一：模型文件本身是可执行载荷

### Pickle 反序列化风险

PyTorch 生态的 `.pth`/`.pt` 模型文件底层使用 Python Pickle 序列化。**Pickle 反序列化过程可以执行任意代码**——这是语言特性，不是漏洞。安全社区已在 Hugging Face 等平台多次发现携带恶意代码的模型文件：用户 `torch.load()` 加载模型的瞬间，恶意代码即被执行。

### 防御

- **优先使用 safetensors 格式**：纯数据格式，不执行代码，已成为 Hugging Face 默认推荐
- 必须从外部获取 `.pth` 模型时，在**隔离沙箱**中加载，或使用静态扫描工具（如 ModelScan、picklescan）预检
- 模型文件来源核验：官方仓库、核对 SHA256、警惕名称相近的"山寨仓库"（Typosquatting）

## 风险面二：Python/ML 依赖生态

AI 项目的依赖树通常又深又重（torch → CUDA 库 → 各种算子包），且 ML 社区习惯从 notebook、个人仓库、PyPI 小包拼装环境：

- **PyPI 投毒**：恶意包伪装成热门 ML 库（typosquatting），安装即窃取凭据
- **依赖混淆（Dependency Confusion）**：内部私有包名被人在公网 PyPI 抢注，构建时被"偷梁换柱"
- **Jupyter/nbconvert 等工具链漏洞**：渲染恶意 notebook 可致 XSS/RCE

### 防御

- 锁定版本 + 哈希校验（`pip install --require-hashes`）
- 内部 PyPI 镜像 + 命名空间隔离，杜绝依赖混淆
- 镜像构建阶段接入 SCA 扫描；模型训练/推理容器以最小权限运行

## 风险面三：训练与 RAG 数据

- **训练数据投毒**：爬虫抓取的语料中可被植入后门触发器
- **RAG 知识库投毒**：能写入知识库的任何入口（客服工单、用户上传、抓取网页）都可能被植入恶意指令，进而劫持检索结果（间接提示词注入）
- **数据合规**：训练语料中的个人信息、版权内容存在法律风险

### 防御

- 数据来源审计与血缘记录；微调数据人工抽检
- RAG 入库侧：内容审核 + 权限控制 + 定期"排毒"（用已知注入特征扫描存量向量库）
- 建立模型/数据版本的可追溯机制（MLflow 等），出问题可回滚可定位

## 企业级防御清单

| 层面 | 措施 |
|---|---|
| 准入 | 模型/依赖统一从受信源获取，建立内部模型仓库 |
| 检测 | 模型文件扫描（ModelScan）+ 依赖扫描（SCA）接入 CI |
| 运行时 | 推理服务沙箱化、网络出向白名单、最小权限容器 |
| 治理 | AI-BOM（模型与数据集清单）、来源登记、变更评审 |
| 合规 | 生成式 AI 服务履行算法备案与内容标识义务 |

## 小结

AI 供应链安全的特殊性在于：**模型权重 = 代码，训练数据 = 配置，提示词 = 输入**——三者都是攻击面。用传统软件供应链的成熟方法论（SBOM、来源核验、最小权限）覆盖这三条新通道，是当前性价比最高的路线。
